## P0：协议、网关与真实 Helper

- 四个核心对象与三种期限：`Credential`、`Binding`、`Session`、`UseLease`；`use_lease_expires_at`、`cache_expires_at`、`provider_credential_expires_at` 分别保存，许可取三者与 Grant、Session 的上限。
- 网关只按登记 Binding 构造上游请求；移除 `X-KeyKoi-*`、`Authorization`、`X-Api-Key` 等中介痕迹后注入真实认证。受控上游统计 `session_tokens=0`，即上游从未收到中介会话令牌。
- 拒绝路径：无令牌 401、未登记路由 404、越模式 `USE_NOT_ALLOWED`、锁定 503、跨 origin 重定向不被跟随、WebSocket/gRPC 升级 501。
- 真实 Helper：AWS CLI 2.41.0 以 `credential_process` 调用 `keykoi helper aws`，成功向受控 STS 端点完成 SigV4 认证；CLI 自身缓存目录 `~/.aws/cli/cache` 的行为已记录（该缓存属于工具行为，是运行时交付边界的明确代价）。
- 实测（同机、受控上游、20 次，单位 ms）：代理 TTFB p50 0.213 / p95 0.249，直连 p50 0.088 / p95 0.100；流式响应首块 0.172ms、完整结束 485ms，证明首块先于响应结束返回。

## P1：单机版

- 密钥库：每版本 DEK + 根密钥包装（AES-256-GCM，Argon2id 派生 KEK）；SQL/WAL/备份中无测试凭证明文；并发轮换时每次读取都来自完整版本；篡改密文返回 `CREDENTIAL_UNAVAILABLE`；恢复保持锁定且 Grant 进入待复核，复核前拒绝用钥，旧会话不复活。
- 会话与 Broker：Unix socket 以目录 0700、socket 0600 与 `LOCAL_PEERCRED`（macOS）校验同用户；管理权与用钥权分属不同主体；只持引用/伪造令牌/过期会话/越模式一律拒绝；版本切换与撤销使旧许可失效；审计只含元数据。
- 网关：Bearer、API Key、Basic 三种注入；保留路径编码与重复查询参数；真实 curl 走完整链路；直连/代理对照测量见 `artifacts/p1-management/measure.json`。
- 运行时交付：真实 Helper 与仅环境变量路径（AWS CLI）各跑一次；取消在 1s 内终止进程树；异常退出码 9 原样返回；残留后代被回收并报告；并发两账户互不串用；轮换后旧值失效；服务重启后锁定并要求解锁。
- 工具接入：严格 Manifest（未知字段拒绝）、脱敏预览、只改受管字段、配置 0600、重复 apply 幂等、真实 AWS 验证、外部改动触发 `CONFIG_DRIFT`、版本超出已验证范围保持 `unverified`、撤销恢复原配置并保留无关字段。
- 管理与发布：管理 CLI 与 Web UI（Host/Origin/CSRF 校验，管理 API 无令牌 401）；launchd 安装、升级、重启；锁定/恢复/复核全流程；`p1-management` 24 项检查全部通过。

## 额外：Touch ID 解锁与授权策略

- 根密钥是 32 字节随机值，由 Swift 助手写入 macOS Keychain，条目 ACL 使用 `biometryCurrentSet`；Touch ID 通过后由系统把根密钥交给 keykoid。指纹不参与密钥派生，新增或删除指纹会使条目失效，主密码始终是唯一恢复入口。
- 授权策略：`once`（默认，同一会话验证一次） / `window:<秒>`（验证后窗口内复用） / `per_use`（每次用钥都验证） / `permanent`（不验证，需二次确认）。验证状态只驻留内存 `AuthCache`，锁库、撤销、轮换与服务重启都会清空。
- 生物识别不可用或非 GUI 会话时回退主密码（显式回退，每次只能证明一次用钥）；回退也不可用时返回 `AUTH_UNAVAILABLE`（HTTP 503）明确拒绝，不静默放行。用户取消返回 `AUTH_REQUIRED`（HTTP 401）。
- 验收（`biometric-auth.sh`，65/65）：四种策略语义、锁定/撤销/轮换清空、助手不可用时的回退与拒绝、审计 `auth_method`/`auth_result`、管理 HTTP 状态码与 UI 控件。自动化使用 `tests/fixtures/biometricstub` 作为助手替身，不依赖真实指纹。
- 真实 Keychain：`available` 在本机通过；`store/load` 需要带 `keychain-access-groups` 权限的签名助手。裸编译产物被系统以 `errSecMissingEntitlement(-34018)` 拒绝，裸二进制即使签名也会被 AMFI 在启动阶段杀死，因此助手改由 Xcode 工程产出 `KeyKoi Biometric.app`（`LSUIElement`，`Contents/MacOS/keykoi-biometric`，entitlements `$(AppIdentifierPrefix)com.keykoi.biometric`，内嵌描述文件），`build-biometric-app.sh` 用 `xcodebuild -allowProvisioningUpdates`（Team `977QNJU6V6`）自动签名并把 `KEYKOI_BIOMETRIC_HELPER` 打印给 keykoi/keykoid。`biometric-app.sh` 实测 `launch_probe=ok`、`store/load` 同值往返、`keykoi vault enroll-biometric` 与 `keykoi auth status` 报 `available=true`；只剩系统指纹对话框需要人工点按，命令见 `artifacts/biometric-app/result.json` 的 `manual_steps`。

## P3：多设备中心（本机拓扑）

- PostgreSQL 中心：设备注册（一次性 bootstrap 令牌）、设备 HMAC 签名租约、在线确认、撤销事件、授权代次。
- 实测：两个独立注册设备分别通过在线认证；设备撤销在下一次请求即生效（记录毫秒级传播时间）；绑定撤销同样即时阻止；短期模式在中心失联后仍可用至原绝对截止，随后停止（记录剩余秒数）；中心重启轮换代次后旧租约无法再确认，设备重新取租约后恢复。
- 中心在凭证版本变更后拒绝旧版本租约（`LEASE_STALE`），客户端自动换新租约，新租约携带新版本；同一请求仍只使用同一版本完整字段。

## 额外工具验证：阿里云 CLI

注意：`aliyun-cli` 的 `~/.aliyun/config.json` 中的 AK 配置文件**优先于环境变量**（实测：两者同时存在时使用配置文件里的 AK）。因此验收与 shim 都用 `--config-path` 指向一个不存在的托管路径来隔离它；如果本机已有明文 profile，`keykoi shim install` 会给出警告。

`aliyun-cli 3.5.3` 通过 `keykoi run` 的环境注入取得 `ALIBABA_CLOUD_ACCESS_KEY_ID`、`ALIBABA_CLOUD_ACCESS_KEY_SECRET`、`ALIBABA_CLOUD_SECURITY_TOKEN`，用真实 CLI 的 HMAC-SHA1 签名访问受控 HTTPS 上游（自签测试证书，未访问真实阿里云端点）。上游确认：`AccessKeyId` 与 KeyKoi 交付值一致、`Signature` 存在、`SecurityToken` 字段到达、KeyKoi 中介令牌未出现、运行后许可撤销且进程树干净，工具 home 无明文秘密。

使用真实账号时：

```bash
keykoi credential add --kind access_key_pair --label "aliyun account" \
  --field access_id --field access_secret        # 值走隐藏输入，或加 --field-stdin 从 stdin 读
keykoi binding add --id bind_aliyun --credential <cred-id>   --origin https://ecs.cn-hangzhou.aliyuncs.com --route aliyun-ecs --scheme bearer
keykoi grant add --principal "principal_local_$(id -u)" --binding bind_aliyun --mode runtime_delivery
keykoi run --binding bind_aliyun --exe "$(command -v aliyun)"   --env ALIBABA_CLOUD_ACCESS_KEY_ID=field:access_id   --env ALIBABA_CLOUD_ACCESS_KEY_SECRET=field:access_secret   --env ALIBABA_CLOUD_SECURITY_TOKEN=field:session_token   -- ecs DescribeRegions --region cn-hangzhou
```

阿里云的 RPC 请求把签名放在查询串里（`SignatureMethod=HMAC-SHA1`），因此不能靠改 Header 的网关代理完成认证；该工具的正确接入模式是运行时交付，这也是验收里用 `keykoi run` 而不是网关的原因。

### 无感入口（PATH shim）

安装一次后直接输入 `aliyun ...`，不再需要 `keykoi run` 前缀：

```bash
keykoi shim install --name aliyun --exe "$(command -v aliyun)" --binding bind_aliyun \
  --env ALIBABA_CLOUD_ACCESS_KEY_ID=field:access_id \
  --env ALIBABA_CLOUD_ACCESS_KEY_SECRET=field:access_secret \
  --env ALIBABA_CLOUD_SECURITY_TOKEN=field:session_token \
  --prepend-arg=--config-path \
  --prepend-arg="$HOME/Library/Application Support/KeyKoi/shims/aliyun.no-config.json" \
  --update-shell          # 向 ~/.zshrc 写入受管 PATH 片段（可用 --shell-rc 指定）
source ~/.zshrc
aliyun ecs DescribeRegions --region cn-hangzhou
```

实现要点：shim 是放在 `<数据目录>/shims/` 的符号链接，指向 keykoi 二进制；启动时按 `argv[0]` 识别，读取 0600 安装记录（真实二进制绝对路径、Binding、环境映射、前置参数，不含凭证），经 IPC 取得 `runtime_delivery` 许可后执行真实工具。参数数组、stdio、退出码与信号语义都保留；`version`、`--help`、`configure` 等本地命令不取凭证，daemon 不在时也能用。`keykoi shim list` 查看，`keykoi shim remove --name aliyun --update-shell` 还原。

配置隔离：`--prepend-arg` 会在需要凭证的调用前插入固定参数（如 `--config-path <不存在的路径>`），用于绕开工具自带的明文配置文件。若用户自己传了同名前缀参数，shim 直接拒绝并提示改用 `keykoi run`，避免静默绕过 KeyKoi。验收覆盖：已有明文 profile 被忽略且原文件不被修改、托管配置路径不落盘、静态 AK/SK 与 STS 两种组合、`configure list` 仍读取真实配置。

| OAuth access/refresh token | 提供方适配 + 网关 | 受控 OAuth 提供方 | 见 P4 OAuth 验收（轮换、撤销、恢复） |
| OAuth2 `client_credentials`（`client_secret_basic` / `client_secret_post`） | 显式 HTTP 网关（`oauth_client_credentials`） | 受控 token 提供方 + 受控上游 | 两次网关请求只换取一次 token；缓存过期后重新换取；错误 `client_secret` 为 401 且不泄露 |
| GCP 服务账号 JWT 断言（RS256） | 显式 HTTP 网关（`oauth_jwt_bearer`） | 受控 token 提供方（独立验签） | 断言签名可被公钥验证；越权 scope 被拒；上游收到签发的 Bearer |
| SSH 私钥 | SSH agent | OpenSSH 10.3p1 | 见 P4 SSH 验收 |
| 数据库密码 | PostgreSQL 协议代理 | 真实 psql / pgx | 见 P4 数据库代理验收 |

说明与边界：

- 不支持把密钥放进**查询参数**（例如 Gemini 的 `?key=` 形态）由网关注入；这类客户端需改用同等的 Header 形态（Gemini 支持 `x-goog-api-key`），或走运行时交付。原因是不对整段 URL 做字符串替换，避免破坏签名与重复参数语义。
- 模型 API Key 走网关时，工具与 Agent 只持有中介会话令牌；真实 key 只在网关向上游发请求时注入。服务进程的推荐接法见 [[docs/指南/接入模型服务|把服务接入模型 API]]。
- 需要请求内签名的密钥（AWS SigV4、阿里云 HMAC-SHA1）不能靠 Header 网关替换，必须走 `runtime_delivery` 或专用签名器。

## P4：专用协议

- SSH Agent：`ssh-add -l` 枚举其 binding 下具 sign 许可的密钥；真实 sshd 公钥登录成功；`ssh-keygen -Y sign/verify` 对 ed25519/rsa 均通过；撤销后枚举为空、新连接失败、既有连接完成（按实际结果登记）。私钥只在受信进程内解析并清零。
- 专用签名：AWS SigV4；6 个官方测试向量通过；受控校验上游用同一 secret 独立重算通过；真实 AWS CLI 的 `s3api` 请求签名与 `keykoi sign` 结构一致。预签名、分块/流式、非 S3 已编码路径按设计拒绝。
- OAuth：授权码 + PKCE + refresh 轮换；并发刷新只有一次上游调用与一次版本提交；撤销、网络失败、上游成功但本地提交失败三种异常可区分且状态可见；令牌不进入工具配置或日志。
- 数据库代理：PostgreSQL 协议；客户端用会话令牌代替数据库密码，代理以 SCRAM-SHA-256 完成上游认证；真实 psql 与 pgx 扩展协议均通过；取消、关闭、错误令牌、无许可、上游 TLS 校验均验证；真实密码不出现在日志。
- 受信 TLS 代理：仅登记域名可 CONNECT；终止客户端 TLS 后注入认证并验证上游证书；未登记域名 403 且上游 0 请求；客户端不信任代理 CA 与上游证书错误分别终止；会话令牌不泄露给上游。

## 未达成与已知限制

- Linux 文件隔离（P0/P2）与 Windows 验收按路线图延期。
- 预签名、分块/流式请求体签名、非 S3 已编码路径签名明确不支持；AWS CLI 对照仅到本机受控上游，未访问真实云端点。
- TLS 代理支持 HTTP/1.1；HTTP/2、WebSocket、HTTP/3 与证书固定不支持。代理不再自行解锁密钥库：用钥决定经本机 IPC 交给 keykoid，因此 `keykoi lock` 之后代理请求返回 `VAULT_LOCKED`，但代理本身需要 keykoid 正在运行。CA 尚未托管进密钥库。
- 数据库代理仅 PostgreSQL 有端到端验收；MySQL/MongoDB 段需要 docker 才能跑（本机无 docker 时跳过）。Redis/MySQL 上游默认要求可验证 TLS，明文上游必须显式 `--upstream-insecure`；MySQL 在明文链路上不做 `caching_sha2_password` 完整认证（不再使用服务端临时 RSA 公钥）。不支持客户端侧 TLS、SCRAM 通道绑定、SQL 语义授权与连接池复用；Binding 仍以 HTTP origin 占位登记数据库端点。
- P3 的本机拓扑不覆盖跨物理主机网络差异；休眠恢复与显著时间偏差未单独注入验证；中心只发放许可，不保存业务凭证内容。
- 会话与许可是进程内状态；重启后需要重新解锁与重新建立会话（设计如此，不是缺陷）。网关为每个请求申请并立即释放一次许可；代理的许可在连接结束时撤销。
- 中心默认只监听回环；跨机器部署必须提供 `--tls-cert/--tls-key`，且设备注册令牌（`--bootstrap-token`）必须与管理令牌分开。
- OAuth 只覆盖标准提供方；闭源客户端登录态导入不在范围。
